**改了 langchat 代码之后的标准动作**（这就是这套东西存在的意义）：

```bash
# 1. 先把改动前的状态测一遍存档（用新 tag，别覆盖老的）
python eval/a5_eval.py all --tag 改动前

# 2. 改代码 → 重启 server.py
# 3. 再测一遍
python eval/a5_eval.py all --tag 改动后

# 4. 拉平对比（噪声带会自动算）
python eval/a8_compare.py baseline 改动前 改动后 --out 对比报告.md
```

**⚠️ 第 4 步有两个坑，都会让结论失真：**

- **第一个 tag 被当作 baseline。** `a8_compare.py:61` 写死了「第一个作为 baseline，其余依次对比」——
  Δ 表、修复矩阵的反查都拿 `args.tags[0]` 当参照。所以**必须 `baseline` 打头**。
- **🔴 噪声带是从「传进去的 tag」里现算的**：`_cond()` 会把**同语料 + 同配置**的 tag 两两配对，
  再用它们的差估出噪声带。所以**如果传进去的 tag 里一组"同条件重跑"都没有，噪声带就是 0**
  —— 那时候**任何 0.001 的差别都会显示成"显著"**，正是这次差点栽进去的坑。
  所以对比时至少带上 `baseline_repeat` 或 `baseline_run2`（现成的两组同条件重跑），
  或者临时 `--tag 名字A` / `--tag 名字B` 跑两遍同一个配置：

```bash
# 想只比"改动前 vs 改动后"？把同条件重跑一起传进去，噪声带才有意义
python eval/a8_compare.py baseline baseline_repeat baseline_run2 改动前 改动后
```

## 设计说明

### 为什么拆成 collect / score 两段

`collect` 走真接口（真检索、真调 DeepSeek 生成），贵在"真实"，一次采集要能反复用；
`score` 是折腾段（换指标、调裁判、重算），而它跑几百次 LLM 调用、中途挂掉是常态。
两段各自落盘 —— 打分失败不会把采集结果一起带走。

### 为什么每题之前要清聊天历史

chain 是 `RunnableWithMessageHistory`，`session_id` 就是 `user_id`。
不清的话第 20 题的上下文里躺着前 19 题的问答，**等于给模型开卷提示，分数全虚高**。
采集前逐题调 `/api/v1/chat/clear-history`。

### 为什么拒答型不参与任何 RAGAS 指标

拒答型在这套指标下**被结构性判负**，两处都吃亏：

- 它的 reference 是"文档里没有，应当拒答"，**结构上不可能出现在检索上下文里**
  → context_recall / context_precision 必然为 0；
- 它的答案是"无法回答"，而 `ResponseRelevancy` 对 noncommittal 回答**直接给 0**
  → answer_relevancy 也必然为 0。

所以混进均值不是"平均"，是拿 8 道注定 0 分的题去拉低整体。拒答题只回答一个问题：
**该拒的时候有没有老实拒** —— 那就是拒答率。

| 指标 | 算什么题 |
|---|---|
| faithfulness | 37 道可答题 |
| answer_relevancy | 37 道可答题 |
| context_recall / context_precision | 37 道可答题 |
| 拒答率 | 8 道拒答题单列 |

### 为了让评测能跑，对项目做的三处改动

1. **`chat_model_handler.py`：响应里多返回一个 `contexts`**
   —— 原来只返回答案和 `file_info_list`，而那个只有文件名没有正文，
   RAGAS 的 faithfulness / context_recall / context_precision 全都需要检索原文，算不了。
2. **`scripts/init_db.py` + 库里的 `threshold_vector`：0.5 → 0.6**
   —— 见 `../langchat/环境搭建记录.md` 坑 7。不修的话白话文问题检索静默返回 0 条，
   baseline 分数测的是那个常量，不是系统。
3. **`threshold_fulltext`：0.05 → 0** —— 见坑 8。**不修的话 `hybrid` 是静默无效的**
   （全文那一路被阈值全砍，45 题里 38 题返回 `[]`，整个混合检索与纯向量逐字相同）。
   > ⚠️ **但 0 也不对，见坑 11**：它让全文那一路从「什么都不返回」变成「什么都返回」，
   > 直接造成 C01 的倒退。**这个项目里没有哪个绝对阈值是对的** —— 根因是 `to_query`
   > 把虚词放进了检索词表，导致排序本身没有区分度。
   > 所以这次把 0.05 改成 0 的定位是：**一个「让下一个 bug 显形」的中间态**，
   > 不是最终修法。真正的修法挂在「A7 挂起项」第 1 条。

> ⚠️ 1 和 2、3 性质不同：1 是**为评测加接口**，2 和 3 是**修真实 bug**。
> 记这个区别是因为 baseline 的口径必须是「修掉致命常量之后、其余保持原样的系统」——
> 否则测出来的是那个常量，不是系统。

## 踩过的坑

### 坑 1｜`import ragas` 直接炸

```
ModuleNotFoundError: No module named 'langchain_community.chat_models.vertexai'
```

ragas 0.4.3 在 `ragas/llms/base.py:12` 硬导入它，而 langchain-community 0.4 已经删掉了。
这个符号只在 `MULTIPLE_COMPLETION_SUPPORTED` 里参与一次 `isinstance` 判断，
所以 `_compat.py` 往 `sys.modules` 里塞一个占位类就行（**必须在 `import ragas` 之前**）。

### 坑 2｜⭐ DeepSeek 不支持 `n > 1`，整组 answer_relevancy 全 400

```
Invalid n value (currently only n = 1 is supported)
```

ragas 的 `ResponseRelevancy` 默认 `strictness=3`（每个答案生成 3 个问题），
而它是通过 `n=3` 传给 LLM 的（`_answer_relevance.py:143`）。**DeepSeek 只支持 n=1**。

→ 必须显式 `ResponseRelevancy(..., strictness=1)`。
这是"把裁判换成 DeepSeek"的第二个坑，清单里只提到了第一个（默认要 OpenAI key）。

### 坑 3｜ragas 装完把 langchat 的依赖降级了

`ragas` 把 `langchain-openai` 从 1.6.1 降到 1.1.9，而 `langchain-deepseek` 声明要 `>=1.3.1`。
实测暂时能跑，但版本声明已经冲突 —— **评测线和运行线共用一个 venv 是脆弱点**。

### 坑 4｜⭐ 我的聚合写法把指标互相覆盖了（最坑的一个）

第一版写的是 `scores.update(_score_group(...))`。`scores` 的键是题面、值是「指标字典」，
所以顶层 `update` 是**替换**而不是**合并** —— 后一组会把前一组的同名题面整个盖掉。

表现极具迷惑性：三组分别算 45 / 45 / 37 题，最后只剩 37 题带着 context 指标、
**恰好 8 题带着 answer_relevancy**（45 − 37 = 8），faithfulness 一条不剩。
那 8 题刚好全是拒答题，看起来像"拒答题的特例行为"，实则是覆盖顺序的产物。

→ 改成按题面 `setdefault(ui, {}).update(d)` 逐项合并。

### 坑 5｜NaN 污染整个均值

`agg()` 原本只写了 `if v is not None`。但 pandas 的 NaN 是 `float`、也不 `is None`，
会被放进 `sum()`，**一个 NaN 就把整个均值变成 nan**。
表现是 context_precision 明明有 35 个有效值，报出来却是 nan。

→ 过滤条件改成 `isinstance(v, (int, float)) and v == v`（`v == v` 用来排 NaN）。

### 坑 6｜ragas 默认 180 秒超时，DeepSeek 偶发超时

一次 74 个 job 的跑分里有 2 个 `TimeoutError`，对应题目的该项指标就留空。
→ `RunConfig(timeout=600, max_retries=3)`。

### 坑 7｜⭐⭐ `context_precision` 在**跨文档题**上结构性为 0，不是检索差

baseline 里 7 道对比题的 `llm_context_precision_with_reference` **全部是 0.000**，
而同一批题的 `context_recall` 是 1.00。看着像矛盾，实则是这个指标的定义决定的。

看 `ragas/metrics/_context_precision.py:148-159`，它逐段问裁判的是：

```python
QAC(question=user_input, context=context, answer=reference)   # ← answer 用的是参考答案
```

即「**这段上下文对得出「参考答案」有用吗**」，再按平均精度加权：

```python
verdict_list = [1 if v.verdict else 0 for v in verifications]
score = Σ(前缀命中率 × 该位命中) / (命中总数 + 1e-10)
```

对比题的参考答案是**跨两篇文档的对比总结**，而任何**单段**只能覆盖其中一篇 —
裁判看到「这段没在对比两者」就判 0，**5 段全 0 → 分子分母同时为 0 → 直接得 0.000**。

实测复现（手工调裁判）：
```
C01 段[1] verdict=0  reason="...does not discuss diet recommendations for weight loss
                                 articles or compare them with health preservation articles"
```

→ **结论：跨文档题的 ctx_prec 是结构性 0，不能读作「检索质量差」。**
读这个指标时只看**事实型**（单文档）那 30 题。真正的检索质量问题要看
`context_recall` + 事实型的 `ctx_prec`。

### 坑 8｜⭐ `answer_relevancy` 会**惩罚「表达不确定性」的正确回答**

`ragas/metrics/_answer_relevance.py:127`：

```python
score = cosine_sim.mean() * int(not all_noncommittal)   # 判成回避 → 整个乘 0
```

而 noncommittal 的定义是「evasive, **vague, or ambiguous**」。
当**正确答案本身**就是「研究有限 / 不能判定 / 没有证据表明」时，答案忠实地复现了它，
却容易被读成 vague → **乘 0**。

实测对照（baseline）：

| 组 | 题数 | answer_relevancy 均值 |
|---|---|---|
| 以「根据现有资料」开头 | 5 | **0.193** |
| 其他 | 32 | **0.965** |

⚠️ 但这**不是**「短语一出现就判 0」—— **C01 同样用这个开头，拿了 0.96**。
真正的分界是**答案里有没有实质内容**：那 5 题里 4 题是真拒答（判 0 合理），
只有 **F15 是明确误判**（答案与参考答案几乎一字不差）。

> 这条对 RAG 场景特别不友好：**RAG 的正确答案经常需要说「文档里只说了这些」**。
> 读 answer_relevancy 时要记得它对这个句式有系统性的向下偏差。

### 坑 9｜真实缺陷：chunk 边界会切断实体名

`F14` 问「蜂王浆中具有抗菌抗炎作用的特有成分」，答案是：

> 根据现有资料无法回答。文档中仅提到蜂王浆含有「**王浆酸（10 -**」，但内容不完整……

引文被**从中间截断**了 —— `10-HDA` 和「抗菌抗炎」落在另一个 chunk 里没被召回。
**模型没错，是分块策略把答案切成了两半。**

→ 这类题在 faithfulness / answer_relevancy 上都会被判负，
但它反映的是**分块（chunking）质量**，不是生成或检索质量。
A7 的候选改造项里应当有「分块策略」一席。

### 坑 10｜⭐⭐ 同配置重跑：**措辞全变，结论不变**

改完 `order` 那组（`keep_retrieval_order=1`，检索上下文与 baseline **逐字相同**、
只是顺序不同）发现它把 F14、C07 两题从「答不出」变成了答得出。
我第一反应是「这肯定是 `temperature=0.5` 的生成抖动，不是排序的功劳」——
**差点就这么写进报告**。于是补了一组同配置重跑（`baseline` vs `baseline_run2`）来验证。

结果反过来：

| 对比项 | 结果 |
|---|---|
| 检索上下文 逐字相同 | **45/45** —— 检索侧完全确定性 |
| 答案 逐字相同 | **20/45** —— 56% 的答案换了措辞，最低相似度 0.468 |
| 「答不出」的题号 | **完全一致（F14/C03/C07），零翻转** |

两条结论，都需要：

1. **检索是确定性的**（45/45），所以任何「上下文变了」都能**确定地**归因给改造 ——
   这是整个实验设计的地基。
2. **生成端抖得很厉害，但只抖措辞、不抖定性**：一半以上的答案文本不一样，
   可是「答得出 / 答不出」这个二元判断两次完全一致。
   → 所以 `order` 那两处翻转**确实来自排序**，不是抖动。

> 💡 方法论：**RAG 评测里要分清「文本相似度」和「结论稳定性」**。
> 前者噪声极大（56% 变），后者可以很稳（0 翻转）。
> `faithfulness` / `answer_relevancy` 这类基于文本比对的指标吃的是前者，所以噪声大；
> 「答不出题数」「拒答率」「命中哪一段」吃的是后者，所以可以当硬证据。
> **报告要站在硬证据上，用软指标做参考。**

> ⚠️ 反过来也要留个心眼：零翻转是**两次重跑**的结果，
> 说明翻转**罕见**，不等于**不可能**。所以单次跑出来的 1 题差异，仍然只当线索。

### 坑 11｜⭐⭐⭐ 全文检索的**根因**：查询词表里全是虚词，所以相关段落在 rank 上分不开

这条是坑 8 的**真正底牌**。我原先只诊断到「阈值 0.05 把全文通道全砍了」，
于是把阈值改成 0 —— 结果 `hybrid` 从「静默无效」变成「**灌垃圾**」：
C01（问养生/减肥的饮食建议）召回了 `宴桃园豪杰三结义`、`用奇谋孔明借箭`，
模型被带偏，直接答「根据现有资料无法回答」——
而 baseline 用纯向量是**答对**的（且三次重跑都答对）。**我制造了一个倒退。**

**实测 C01 的全文 rank 排名**（`426c2b35` 语料，阈值设 0）：

| 排名 | 文件 | ts_rank |
|---|---|---|
| 1 | `宴桃园豪杰三结义.txt` ← 三国 | 0.01949 |
| 2 | `用奇谋孔明借箭 献密计黄盖受刑.txt` ← 三国 | 0.01949 |
| 3 | 蜂王浆对肺结节有没有影响.txt | 0.01949 |
| 4 | 养生时代来临，怎么养生.txt ✅ **相关** | 0.01870 |
| 7 | **减肥陷阱.txt** ✅ **相关** | 0.01497 |
| 8 | `宴桃园豪杰三结义.txt` ← **三国** | **0.01497 ← 与第 7 名完全并列** |

**相关段落在第 4、7 名，三国段落在第 1、2、8 名 —— 两者的 rank 区间完全重合。**
所以任何绝对阈值都无解：`0.05` 全砍（坑 8），`0` 全放（本坑）。

**根因（`src/utils/ts_vector.py:96 to_query`）**：

```
C01 的 tsquery = 减肥 | 文章 | 和 | 养生 | 文章 | 在 | 饮食 | 建议 |
                 上 | 各 | 侧重 | 什么 | ？ | 有 | 什么 | 区别 | ？
```

四个缺陷叠在一起：

1. **没有停用词表** —— `和 / 在 / 上 / 有` 是中文虚词，**任何一段中文都含**，
   于是 `减肥 OR 和 OR 在 OR …` 几乎召回全库。
2. **`remove_chars` 的用法是错的**（`ts_vector.py:18`）：它是个**字符串**，
   而判断写成 `token not in remove_chars` —— 这是**子串匹配**，不是集合成员判断。
   而且全角 `？` 根本没写进那个字符串（`！` `：` `；` `，` 都在，独独漏了它），
   所以 `？` 活下来当了检索词。
3. **`|` 是纯 OR**：命中任一 token 就算命中，无「命中了几个」的概念。
4. **`ts_rank` 由高频虚词主导**，于是**文本越长、虚词越多，rank 越高** ——
   这正是三国演义（长篇古典白话）霸榜第 1、2、8 名的原因。

> ⭐ **所以正确的修法不是「再调一个阈值」**，而是修 `to_query`：
> 过滤停用词 + 改 `cut_all=False` + 查询用 `&`（或至少按「命中了几个实词」排序）。
> 这同时解释了**为什么绝对阈值在这个项目里注定失败** ——
> 它不是我之前以为的「阈值选得不好」，是**排序本身没有区分度**。
> 这也把挂起项「阈值策略：绝对 → 相对/秩基」升级成了更根本的一条：
> **先把排序修出区分度，再谈阈值。**

> ⚠️ 附带的实验纪律教训：`threshold_fulltext: 0.05 → 0` 这个「修复」我做得太顺手了 ——
> 只验证了「它不再静默无效」，**没验证「它变好还是变坏」**。
> 是 `hybrid` 组的**负向结果**（C01 答不出）把它揪出来的。
> **能修好一个「什么都不做」的 bug，不等于修对了** —— 要有指标敢说它变坏了。

### 坑 12｜⭐⭐⭐ 我的「真答不出」判据**两个方向都错**，而且刚好把两组的差距抹平了

「硬指标」那一列（可答题里模型明说答不出的题数）是**这整份评测的最终裁判** ——
因为四个 RAGAS 指标全被噪声盖住，只剩它还能定性。
我一开始的规则是「答案开头是『根据现有资料无法回答』**且**短于 80 字」。
结果这唯一一根标尺上，两头都错，各抓一例：

| 错法 | 实例 | 原文说了什么 | 真相 |
|---|---|---|---|
| **误判成「答了」** | `rerank_strict` 的 F14，**99 字** | 「…但并未明确说明…因此**无法给出确切答案**」 | 是**长拒答**，它没答，只是啰嗦 → 少算了 1 题 |
| **误判成「答不出」** | `combo` 的 C05，**238 字** | 「…**说明：文档中确实分别介绍了** `jiebacfg` 和 `jiebaqry` 的区别（…）…」 | 区别**说全了**，只是被检索混进来的无关段落弄得不敢确认 → 多算了 1 题 |

两个错误一起发生，效果是：真实 **0 vs 2**，被我算成 **1 vs 1** —— **差距被完整抹平**。

这直接改了两个结论：
- `combo` 的 0/37 是真的，但**它是「长答案被逼成拒答式开头」的受害者**，
  而 C05 这个失败模式的成因是**检索垃圾**（`hybrid` 那一路塞进来的无关段落），不是模型不行；
- `rerank_strict` 其实**没修好 F14**，真答不出是 **2** 不是 1，`结论二` 里它和 combo 的对比要按 0 vs 2 读。

**修法**：不再用长度猜 —— 脚本改成 `MANUAL_LONG_ANSWERED` **逐条登记**人工判读结果，
未登记的长答案打印告警（保守当答不出算）；并且把**所有**拒答式开头的答案原文
连同判定一起贴进报告（折叠块），让判读**可复核**。

> 教训：**这根标尺比它看起来主观。** 它顶着「纯字符串、不过裁判、绝对客观」的名头，
> 但「到底答没答」本身是个语义判断 —— 字符串规则只是把这个判断藏起来了。
> 更刺眼的是它错得**方向相反**：一个抬高了对手、一个压低了自己，于是刚好抵消。
> **两边同向的误差会被看出来，反向的误差会互相抵消、看起来像「没问题」。**

### ⭐⭐ 第 4 项改造：分块策略 —— 唯一一条「缺陷 → 定位 → 对照实验 → 根因」全走通的链

这条线索是整个评测里证据最硬的，完整记录：

**① 症状**：`F14`（问「抗菌抗炎的特有成分」）答「根据现有资料无法回答」，
faithfulness 0.73。它说「文档中仅提到蜂王浆含有『**王浆酸（10 -**』，但内容不完整」——
**引文从中间断了**。模型其实在告诉我们答案。

**② 定位**：`10-HDA` 被分块边界劈成两半，分别落在两个 chunk 的首尾：
```
chunk#2 结尾:  ...其特有的王浆酸(10 -
chunk#3 开头:  - HDA),具有抗菌、抗炎、调节免疫等生物活性...
```
而**只有 #2 被召回**。#3 全文只有 73 字、开头就是残句，**这种 chunk 永远不可能被召回**。

**③ 对照实验**（唯一变量 = 多喂一段）：
```
① baseline 原 5 段        → 「根据现有资料无法回答」              ← 复现失败
② 原 5 段 + 那个碎片 #3   → 「…特有成分是**王浆酸（10-HDA）**」  ← 完全答对
```
**失败 100% 归因于分块，与模型无关、与排序无关。**

**④ 根因**（查原文后确认，和我最初的推断**不一样**）：
原文是**一整段连续文本**（`蜂王浆…txt` 共 1473 字，**无换行**）：

```
原文:  ...其特有的王浆酸(10 - HDA),具有抗菌、抗炎、调节免疫等生物活性...
```

默认 separators 是 `["\n\n", "\n", " ", ""]` —— 对这段文本，`\n\n` 和 `\n` **都切不动**，
于是跌到第三级**按 `" "` 切**。而中文里空格极少，**`10 - HDA` 中间那个空格就成了唯一可用的切点**，
刀正好落在这里。

> 之前我误判为「原文有 `\n\n` 段落分隔」—— 查了 uploads/ 里的原文，**全库扫描「横杠+换行」= 0 处**，
> 那个推断是错的。真正的机制是「按空格切」。

**⑤ 修法验证**（离线跑，不动数据库）：把 separators 换成中文标点优先：

```python
separators=["\n\n", "\n", "。", "！", "？", "；", "，", "、", " ", ""]
```

结果：**`10-HDA` 回到同一块了**（该块含完整 `10 - HDA`）✅ —— 这一类（词被空格切断）能修。

> ⚠️ 但**整体碎片率没有改善**（12.0% → 12.2%），借箭那篇甚至从 1 个碎片变 3 个。
> 因为「碎片」有**多个不同来源**，加标点只解决其中一类：
> | 来源 | 例子 | 加中文标点能修吗 |
> |---|---|---|
> | 词被空格切断 | 蜂王浆#3（`10 - HDA`） | ✅ 能 |
> | overlap 产生的冗余块 | 减肥#4（37字，前一块尾巴的重复） | ❌ 不能 |
> | 段落本身很短 | 西安交大#17（代码块天然就短） | ❌ 不能 |
>
> **所以完整的修法是两条一起做**：① 标点感知 separators ② 短块后处理（合并回前一块）。

**⑥ 全局量化**：83 段里 **10 段是低质碎片（12%）**，分两类 ——
- **真碎片**（语义残缺，永远召不回）：蜂王浆#3(73字)、西安交大#2(70字)、宴桃园#3(39字)…
- **纯冗余块**（内容几乎是前一块尾巴的重复，白占检索位）：减肥#4(37字)、宴桃园#2(56字)…

**修法（两条都要做，调参不够）**：
1. **标点感知 separators**：`["\n\n","\n","。","！","？","；","，","、"," ",""]`
   —— 让切点落在句子边界，而不是「中文里唯一那个空格」
2. **短块后处理**：< 120 字的块合并回前一块 —— 治的是 overlap 冗余块和天然短段
   （这两类**加标点治不了**，见上表）

**⑦ 拆开跑：两条改动各治什么**（`python eval/a7_chunk_audit.py`，离线、不连库）

`SMART_CHUNKING` **打包了两处改动**，这跟 rerank 那个混淆变量是同一类毛病，
所以补了个 2×2 的离线分解（两种 separators × 合并/不合并）：

| 配置 | 10-HDA 状态 | 碎片块 | 碎片率 |
|---|---|---|---|
| 原始（英文 separators，无合并） | ❌ 两半分在两个块 | 10/83 | 12.0% |
| + **只**加中文标点 separators | ✅ 干净 token | 10/82 | **12.2%** |
| + **只**做短块合并 | ⚠️ 同块但被 overlap 污染成 `10--HDA` | 0/73 | **0.0%** |
| + 两条都做（= 当前代码） | ✅ 干净 token | 0/72 | **0.0%** |

> ⚠️ **这张表推翻了我前面写的归因**，以表为准：
> - **碎片率几乎全靠「短块合并」** —— 只合并直接归零；只加标点反而略升（12.0→12.2%）。
>   我原先说「两条都要做」是对的，但**主次说反了**：合并是主力，标点是收尾。
> - **「词被切断」两条都能治，但只有标点治得干净**。只合并是把两半并进同一块，
>   代价是 overlap 会把那个连字符复制一份，读出来是 `10--HDA` —— 语义能懂，字节不干净。
> - 顺带解释了那个 73 字碎片的来历：**它是 overlap 的产物**，不是原文断段。

> ⚠️ **判据写错会直接翻转结论**，记一笔：这个检查第一版写的是 `"10-HDA" in chunk`，
> 于是把「只合并」判成 ❌ —— 因为合并用 `\n` 拼、overlap 又复制了一个连字符，
> `10 -\n- HDA` 归一化后是 `10--HDA`，差一个字符就不匹配了。
> 现在分成「干净 / 同块但被污染 / 分在两块」三态报，**不把「同块」和「干净」混为一谈**。

> ⚠️ **局限**：这里只有**离线分块审计**，两个子改动**没各自跑端到端评测** ——
> 端到端只验证了打包版（`--tag rechunk`）。所以「哪一条单独就能让 F14 答对」
> 目前只有上面这份离线证据，没有分数背书。要补就是再建两个 collection 各跑一次。

>   而 `rerank`（thr=0.8）那组看起来全面变好，**功劳主要属于阈值放宽，不属于 reranker** ——
>   这正是当初补这组干净对照要回答的问题。

> 📌 **一条更正**（我原先判断错了）：我一开始写「`SearchMode.HYBRID` 在 `search.py` 里是
> **注释掉的**，要写代码才能启用」。错了 —— `search.py` 里被注释掉的 `HybridSearch` 类
> 只是一个**替代实现**；真正在用的 `chat_model_handler.py:_retrieve_chunk_ids`
> **hybrid 分支本来就是完整实现的**（`asyncio.gather` 并行跑向量 + 全文再合并去重）。
> 启用它只需要改 `data_dictionary.search_mode`，**一行代码都不用动**。
> 卡住它的是坑 8 那个全文阈值 —— 所以这一项的真实工作量是「修阈值」，不是「写检索」。

### ⭐ A8 结论

**一、指标**确实**能看出差异，但看出的差异和「哪几题答得出」对不上号。**
分开看四个指标（Δ 表见 `results/对比报告.md`）：

| | 各组怎么动 | 能不能反映「修好了几题」 |
|---|---|---|
| 上下文精确 | **每组都大动**：`order` +0.201、`rerank` +0.259、`rerank_strict` +0.276、`combo` +0.206；`hybrid` −0.134、`rechunk` −0.062 | ❌ 它只反映**排序**，和答不答得出无关 |
| 答案相关性 | 好的组稳定涨 +0.05~+0.07（`rechunk` +0.073 / `combo` +0.068），坏的组基本不动 | ⚠️ 方向大致对，但幅度会被生成抖动盖掉 |
| 忠实度 | **在 ±0.05 内来回摆**，方向还相反（`rerank_strict` −0.018 而 `rerank` +0.047） | ❌ 和修复无关 |
| 上下文召回 | **同样 ±0.05 内摆**（`combo` 修好 3 题却是 −0.018） | ❌ 和修复无关 |

**最能说明问题的是 `rerank_strict`**：它把「答不出」从 3 题压到 **2** 题（只修好 C07），
可忠实度 **−0.018**、上下文召回 **−0.045** —— **修好了一题，两个指标却在跌**。
只看四个 RAGAS 均值，你会判它「无效甚至有害」；看实际修好哪几题，才能知道它到底动没动。

> 这一列也不是自动跑出来的：**「开头拒答」不等于「没答」**，
> 我一开始用「答案短于 80 字」判，**两个方向都错**（详见坑 12）。

→ 所以这份评测真正的裁判是下面这一列：可答题里**开头就是拒答话术、且读过原文确认它真没答**的题数
（长答案没法用规则判，改用逐条人工登记，见坑 12）：

| tag | 真答不出 | 平均耗时 | 平均段数 | 备注 |
|---|---|---|---|---|
| baseline | **3/37** | 1.14s | 4.42 | F14 / C03 / C07 |
| order | 1/37 | 1.22s | 4.42 | 只差上下文**顺序** |
| hybrid | 2/37 | 1.08s | 6.98 | ⚠️ 见下 |
| rerank | **0/37** | **4.06s** | 5.00 | 变量不干净（thr=0.8） |
| rerank_strict | 2/37 | 1.93s | 4.42 | 干净对照（F14 / C03） |
| **combo = order + hybrid + rechunk** | **0/37** | **1.26s** | 6.96 | ⭐ 用了新分块语料 |

**二、没有「全赢」的改造 —— 组合赢在硬指标和速度，reranker 只赢一项，而那一项正好是偏的。**

`combo` 与 `rerank` 都把「真答不出」压到 0，但 4 个 RAGAS 指标是**分裂的**：

| tag | 忠实度 | 答案相关性 | 上下文召回 | 上下文精确 | 真答不出 | 平均耗时 |
|---|---|---|---|---|---|---|
| baseline | 0.930 | 0.860 | 0.937 | 0.412 | 3/37 | 1.14s |
| **combo**（order+hybrid+rechunk） | 0.953 | **0.928** | 0.919 | 0.618 | **0/37** | **1.26s** |
| `rerank`（thr=0.8，变量不干净） | **0.976** | 0.900 | 0.896 | **0.671** | **0/37** | 4.06s |
| `rerank_strict`（thr=0.6，干净对照） | 0.912 | 0.856 | 0.892 | **0.688** | 2/37 | 1.93s |

**和干净对照比**（`rerank_strict`，只差 reranker 一个变量）：
组合在忠实度 **+0.041**、答案相关性 **+0.072** 上明确领先，召回 +0.027 贴着噪声带上沿（读作说不清），
硬指标 **0 vs 2**，速度还快 1.5 倍 —— **只在「上下文精确」上输 0.070**。
**和 `rerank` 那组比**则是反过来的（它忠实度 +0.023、精确 +0.053 赢，组合答案相关性 +0.028 赢）。

> **为什么这个分裂不是「各有千秋」，而是「reranker 只买到一样东西」：**
> 它唯一稳定赢的「上下文精确」是**四个指标里唯一噪声为 0.000 的**（同条件三次重跑逐位相同），
> 所以 +0.276 / +0.070 是**真效应**不是抖动 —— 但它衡量的是**上下文排得整不整齐**，
> 不是答案对不对（坑 7 已说明它结构性偏好短上下文）。
> 而它在另外三项上**要么变差、要么贴着噪声带**。
> 硬指标上它俩确实修好了题（`rerank` 3→0、`rerank_strict` 3→2）——
> **但那笔功劳要拆开算**：干净对照只修好 1 题，另外 2 题是 `rerank` 那组**放宽阈值**挣来的（见结论三）。
> → **reranker 本身买到的是「上下文排漂亮」，代价是相对 baseline 的 1.7~3.6 倍耗时。**

⚠️ 换句话说：**「组合更好」这个结论只对「答得出 + 便宜」这两件事成立，不是全面碾压。**
如果你就是要漂亮的上下文精确度（比如做引用溯源给人看），reranker 仍然是唯一选择。

**三、reranker 确实救回了 F14 —— 但方式是「把切碎的两半拼回来」，而且只在候选池够宽时才行。**

F14 的真实病因：`10-HDA` 被分块**从中间切开**，落进两条不同的 chunk。
baseline 的 top-5 里只有前半截（`…其特有的王浆酸（10-…`），后半截 `-HDA)，具有抗菌、抗炎…` 不在。
三个组的实测对照：

| tag | F14 的候选池（实测） | F14 上下文里有什么 | 结果 | 单题耗时 |
|---|---|---|---|---|
| `rechunk` | 7 段 | 段[2] 有**完整**的 `王浆酸（10-HDA)，具有抗菌、抗炎…` | ✅ 答对（治本） | **0.73s** |
| `rerank` | **17 段**（thr=0.8） | 段[0]=`王浆酸（10-` + 段[3]=`-HDA)，具有抗菌、抗炎…`，**两半被同时排进 top-5** | ✅ 答对（治标） | 3.55s |
| `rerank_strict` | 7 段（thr=0.6） | 只有前半截，后半截**压根不在候选池里** | ❌ 拒答 | 1.51s |

同一个人 reranker、同一个模型，**只因为候选池 7 段 vs 17 段，F14 一个拒答一个答对**。
这正好把 reranker 的能力边界钉死了：**它只能重排已有的候选，不能创造候选。**

→ 所以「reranker 值不值」取决于一个前置问题：**候选池里有没有那条信息？**
- 病因是**分块/召回**（信息根本不在池里）→ reranker 只能靠「多个碎片凑一凑」勉强救，
  而且**必须放宽阈值把候选池撑大**才凑得齐（这就是 `rerank` 组为什么配 thr=0.8）。
- 病因是**排序** → 才是对症的。但这份评测里**没有纯粹由排序造成的失败**（C07 那种顺序问题，`order` 零成本就修好了）。

**四、`hybrid` 是双刃，而且刀刃朝哪边取决于一个更深的 bug。**
它修好了 C03，却把 baseline **三次都答对**的 C01 弄成了答不出 —— 多召回的三段三国演义
把模型带偏了。根因不是混合检索这个思路，是**全文那一路的排序没有区分度**（坑 11）。
→ **所以「混合检索有没有用」这个问题，在当前代码下问不出正确答案** ——
排序还没修出区分度，融合策略还是裸拼接（挂起项 1、2）。

**五、这份评测最该被记住的不是数字，是四次「我差点写错」。**
- 差点把 `order` 的改善当成生成抖动（坑 10）—— 补了同条件重跑才翻过来；
- 差点把 `threshold_fulltext: 0.05→0` 当成纯修复 —— 是 `hybrid` 的**负向结果**把它揪出来（坑 11）；
- 差点把 `rerank` 的分数归给 reranker —— 补了干净对照才发现是阈值的功劳；
- 差点用「短于 80 字」这条字符串规则判「答没答」—— 两个方向各错一例，
  刚好把 `combo` vs `rerank_strict` 的 **0 vs 2** 抹成 **1 vs 1**（坑 12）。

> 前三次靠同一个动作救回来：**多留一组「只差一个变量」的对照，并且敢看负向结果。**
> 第四次不一样 —— 它靠的是**读原文**：
> 一个判据越是顶着「纯字符串、不过 LLM、绝对客观」的名头，越要抽几条出来人眼看一眼。

> ⚠️ **`rerank` 组的变量不干净**（我自己的实验设计失误，如实记下）：
> 它采集时 `threshold_vector` 是 **0.8**，而 baseline / order / hybrid 都是 **0.6**。
> 候选池在这两档差得很远 —— 45 题实测（`threshold_vector` 卡的是**距离** `<=>`，
> 不是相似度，所以 0.6 = 余弦相似度 ≥ 0.4，比名字看起来松）：
>
> | thr | 通过阈值的段数（中位） | **实际候选池**（被 `rerank_candidates=20` 截断后，均值） |
> |---|---|---|
> | 0.6 | 8 段 | **9.8 段** |
> | 0.8 | 54 段 | **19.8 段** |
>
> ⚠️ 注意 **20 这个上限**：0.8 那档中位有 54 段通过，但真正进 reranker 的只有 20 段。
> 所以「放宽阈值」的实际效果是**候选池翻倍**（约 2 倍），不是「从 8 段涨到 54 段」。
> 无论如何变量是脏的：
> **它的分数不能单独归因给 reranker** —— 里面混了「阈值放宽」的效果。
> 补一组 `rerank_strict`（thr=0.6 + rerank）作为干净的单变量对照。
>
> 保留 0.8 那组也有意义：**「放宽召回 + 精排」才是 reranker 的实际部署形态** ——
> 只召回 8 段再精排，reranker 几乎没有可挑的余地。所以两组各有各的用。

> hybrid 耗时反而略低于 baseline，是因为全文检索在 PG 内部完成（GIN 索引 + ts_rank），
> 几乎不占 Python 侧时间；而它多召回的那些段会让**下游 LLM 的 prompt 变长**，
> 那部分成本记在生成耗时里，不在这 1.08s 里。
